## Observed source semantics

1. **Registration owns the caller argument until the DNS entry is cleared.** `dns_req_entry` stores `found` and `arg` in static `dns_requests[]`. `dns_enqueue()` associates distinct request entries with callback arguments, and may coalesce same-name pending lookups into one DNS table entry when `LWIP_DNS_SECURE_NO_MULTIPLE_OUTSTANDING` is active. `dns_enqueue` can return `ERR_MEM` on full table/request slots or PCB allocation failure; these paths differ from successful `ERR_INPROGRESS` registration. [dns.c L259-270](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L259-L270), [L1525-1665](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1525-L1665).
2. **Critical clear-after-callback ordering.** In `dns_call_found()`, `dns_requests[i].found(..., dns_requests[i].arg)` executes **before** `dns_requests[i].found=NULL`; duplicate-host requests may be processed in a loop. The callback's own return cannot itself certify DNS registration quiescence. Further DNS PCB release is conditional under random-source-port mode. [dns.c L1041-1103](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1041-L1103).
3. **Completion contexts have different paths.** Success invokes `dns_call_found` within `dns_correct_response`; error response and retry exhaustion call it with NULL. `dns_clear_cache()` can also call `dns_call_found` across outstanding table entries; it is **not** a scoped cancellation API and cannot be used on a production shared resolver merely to release one token. [dns.c L1260-1297](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1260-L1297), [L1497-1504](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1497-L1504), [L1180-1216](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1180-L1216), [L405-419](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L405-L419).
4. **Registration invokes a query-sending path.** For non-cached names, `dns_gethostbyname_addrtype()` calls `dns_enqueue()`, which invokes `dns_check_entry()`; the new-entry path immediately attempts `dns_send()`. The send error is logged but the request can still be left pending until later retry/timeout. An offline host with no usable network does not prove no DNS request was attempted. `localhost` and numeric/cache `ERR_OK` short-circuit cases do not exercise callback registration/clear. `LWIP_HOOK_DNS_EXTERNAL_RESOLVE` may bypass normal DNS registration and is not a substitute proof. [dns.c L1158-1181](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1158-L1181), [L1652-1665](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1652-L1665), [L1722-1819](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1722-L1819).
5. **Potential actual-core fence, not a proven DNS cancellation API.** `tcpip_thread` dispatches `TCPIP_MSG_CALLBACK` sequentially; `tcpip_try_callback` non-blockingly queues future messages or returns `ERR_MEM`. A fence queued from a DNS callback could run after that DNS call stack finishes **only if** the callback/clear path and fence share proven TCPIP-thread serialization and the fence actually executes. A6b proved the generic nested-callback ordering, not a real DNS callback/registration clear or safe token reuse. [tcpip.c L127-203](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/tcpip.c#L127-L203), [L350-369](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/tcpip.c#L350-L369).
6. **Existing upstream tests do not close this gap.** Pinned `test/unit/core/test_dns.c` tests `dns_setserver`/`dns_getserver`, not `dns_call_found` owner lifetime or a real deferred fence. Default upstream `LWIP_DNS_SECURE` (unless overridden) includes no-multiple-outstanding; project Linux and C3/C6 effective preprocessor flags must be independently inspected, not inferred solely from upstream defaults. [test_dns.c](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/test/unit/core/test_dns.c), [opt.h L1179-1191](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/include/lwip/opt.h#L1179-L1191).

## Gate A7b bounded research and test proposal (not execution authorization)

- **A7b-0 preflight:** determine whether *existing* pinned SDK/test linker/host facilities can execute a normal `ERR_INPROGRESS` DNS registration and subsequent real `dns_call_found()` **with zero external packet emission and with no actual DNS query or socket operation**. Merely disconnecting the host, using `localhost`/numeric `ERR_OK`, calling a fake callback, enabling global cache clear or supplying an external-resolver hook is insufficient. A test-only local interception/loopback-injection mechanism, if contemplated, needs an independently authorized implementation scope and a verifiable zero-I/O guard. If impossible without SDK fork, intrusive instrumentation, new emulator or actual network activity, STOP and preserve the blocker.
- **A7b-1 evidence target if preflight admitted:** record actual core-task ID and event order: registration `ERR_INPROGRESS`, original `dns_requests` callback entrance/return, internal registration clear, deferred fence admission and execution, and status/ownership transitions. Demonstrate a source-grounded way to observe clear-after-callback without unapproved SDK patching; a callback's local `exit_marker` alone is not that observation.
- **A7b-2 negative-path matrix:** immediate `ERR_OK` (no token registered), `ERR_INPROGRESS` completion/error, immediate `ERR_MEM/ERR_ARG/ERR_VAL`, duplicate hostname separate callback arguments, callback after deadline, callback absent, fence `ERR_MEM`, fence queued but delayed/never executed, and resource exhaustion. Only after all references are demonstrably quiescent consider a bounded token-reuse experiment; otherwise retain owner and report exhaustion/availability risk. No automatic teardown/recycle claim.
- **Pass levels:** `SOURCE_CONFIRMED` now; `SDK_DNS_RUNTIME_CONFIRMED` only when a real pinned DNS callback registration/clear is observed in an accepted no-I/O test; `TOKEN_RECLAIM_CONFIRMED` needs independent resource-lifetime evidence, not a mere scheduled fence. Hard synchronous DNS→TCP→TLS→HTTP→close deadline, total caller-return latency and device parity stay `UNPROVEN`.
