## Exact call-path findings

1. **HTTP adapter and state machine — SOURCE_CONFIRMED.** Project `EspHttpTransport::perform()` initializes a fresh client, uses `timeout_ms`, invokes blocking `esp_http_client_perform()`, then synchronously calls `esp_http_client_cleanup()` on success and error; header/preparation failure also enters cleanup. The project does not set `is_async`. Upstream `esp_http_client_perform()` follows connect → header/body send → fetch headers → response body loops; `esp_http_client_fetch_headers()` loops over `esp_transport_read(..., client->timeout_ms)`, and body handling can repeat reads while the peer makes incremental progress. If keep-alive is disallowed, `perform()` itself enters `esp_http_client_close()` before return. Hence each per-I/O timeout is not an aggregate wall-clock deadline. [[ESP-IDF http source L1471–1619]](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/esp_http_client.c#L1471-L1619), [[L1622–1650]](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/esp_http_client.c#L1622-L1650), [[L1101–1142]](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/esp_http_client.c#L1101-L1142).
2. **Blocking connect and hostname — SOURCE_CONFIRMED.** `esp_http_client_connect()` selects `esp_transport_connect(..., timeout_ms)` for this adapter; SSL transport enters `esp_tls_conn_new_sync()` and `esp_tls_low_level_conn()`. The latter calls `tcp_connect()` → `esp_tls_hostname_to_fd()` → synchronous `getaddrinfo()` before socket connect/select timeout applies. `esp_tls_conn_new_sync()` has an elapsed-time check *after* its low-level function returns; that does not interrupt a blocked resolver. `esp_tls_conn_new_async()` also passes through the initial resolver path, so changing only `is_async` does not establish a universal hostname deadline. [[HTTP connect L1688–1707]](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/esp_http_client.c#L1688-L1707), [[transport SSL L104–139]](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/tcp_transport/transport_ssl.c#L104-L139), [[ESP-TLS resolver L221–255]](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L221-L255), [[ESP-TLS low level L488–558]](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L488-L558), [[sync loop L581–603]](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L581-L603).
3. **TLS handshake and destruction — SOURCE_CONFIRMED, not timed runtime.** ESP-TLS reaches `esp_tls_handshake()`, which in the pinned mbedTLS backend delegates to `mbedtls_ssl_handshake()` and can return WANT_READ/WANT_WRITE; no global caller-return guard is shown for a single blocked downstream operation. In the inspected transport teardown, `base_close()` calls `esp_tls_conn_destroy()`, which calls `_esp_tls_conn_delete()`, then socket `close()`, before freeing `esp_tls_t`; `base_destroy()` invokes transport close again (now expected idempotent by reset state). No `mbedtls_ssl_close_notify()` was found in this examined teardown path: do not assume an SSL close-notify timeout here, but do not infer `close()` boundedness. [[ESP-IDF backend handshake L268–315]](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls_mbedtls.c#L268-L315), [[TLS destroy L180–198]](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L180-L198), [[transport SSL close/destroy L332–360]](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/tcp_transport/transport_ssl.c#L332-L360).
4. **Socket close is a separate potentially blocking API message — SOURCE_CONFIRMED.** `lwip_close()` invokes `netconn_prepare_delete()` → `netconn_apimsg(lwip_netconn_do_delconn,...)`. For non-core-locking flow, `tcpip_send_msg_wait_sem()` posts to TCPIP mailbox and waits with `sys_arch_sem_wait(sem, 0)` (no timeout). `lwip_netconn_do_close_internal()` may retry TCP FIN close after `ERR_MEM` even for nonblocking netconn; time/poll counter checks depend on callback/timer progression and signal the waiting semaphore only when the close reaches its completion path. Its retry poll interval switches to 500 ms. This source does **not** prove that a live close will hang indefinitely; it establishes that no independent hard caller-return guarantee follows from per-operation timeout or the close retry counters alone. [[lwIP sockets L817–854]](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/sockets.c#L817-L854), [[api_lib L195–224]](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/api_lib.c#L195-L224), [[tcpip L441–464]](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/tcpip.c#L441-L464), [[api_msg close L1024–1155]](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/api_msg.c#L1024-L1155), [[delete L1166–1250]](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e/src/api/api_msg.c#L1166-L1250).
5. **Resource lifetime and safety boundary.** A7b-R1 finite DNS owner-generation reuse is independently accepted only after real completed callback and executed deferred fence; it does not prove a general resolver cancel, a permanent stall recovery, TCP/TLS cleanup quiescence or memory reclamation on an expired caller. Do not release `esp_http_client`, TLS, socket, event callback state or caller-owned `ResponseCollector`/response buffer from another task while an SDK call may still use it. ## D0 Gate A disposition

| Requirement | Source-supported scope | Decision |
| --- | --- | --- |
| L1: aggregate I/O budget | Per-read/write/connect timeouts exist; repeating reads, hostname resolution, completion waits and close are not covered by one monotonic budget | **UNPROVEN** for existing adapter |
| L2: deadline-expired fail-closed result | D1/A3 synthetic and prior isolated SDK evidence are scoped; a blocked synchronous call may not regain control to publish timeout | **UNPROVEN** for universal caller-return |
| L3: cleanup and quiescence | No independent bound for `close()`/TCPIP completion, nor proof that arbitrary pending callback or resource is reclaimable | **UNPROVEN** |

**Current synchronous hard-deadline design disposition: NO-GO as an implementation-admission claim**, not a claim that every real request hangs. The source-backed counterexample is an indefinitely stalled lower-layer completion that the current caller cannot preempt; the current adapter has no independently proven way to terminate that wait and reclaim every retained resource within the required wall-clock budget. Gate A remains **PENDING / UNPROVEN**, Gate B **HOLD**, Stage 3 sole Hot; Stage 4 Cold and Library readiness `PRESERVED`. No production modification or test execution in this study.

## Additional pinned zero-egress close feasibility — 2026-10-17 read-only continuation

**Provenance:** same project baseline `3a059d28ebf9cf339f947823b0c2a23ca89ebe77`; same pinned ESP-IDF/esp-lwIP revisions above. ### Two independent unbounded caller-side waits

- `netconn_prepare_delete()` calls private `netconn_apimsg(lwip_netconn_do_delconn,...)`. In `api_lib.c`, `netconn_apimsg()` delegates to `tcpip_send_msg_wait_sem()`, which for `LWIP_TCPIP_CORE_LOCKING=0` first invokes `sys_mbox_post(&tcpip_mbox,...)`, then `sys_arch_sem_wait(sem,0)`. [[pinned api_lib.c L117–138]](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/api_lib.c#L117-L138), [[pinned tcpip.c L442–464]](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/tcpip.c#L442-L464).
- The pinned ESP-IDF FreeRTOS lwIP port maps `sys_mbox_post()` to `xQueueSendToBack(..., portMAX_DELAY)` and maps `sys_arch_sem_wait(sem, 0)` to `xSemaphoreTake(..., portMAX_DELAY)`. Therefore **both mailbox admission (queue-full) and post-admission completion (core callback stalled / delayed FIN retry)** can block a synchronous caller without a separate operation deadline. This is **SOURCE_CONFIRMED**, not a claim that an actual indefinite stall was observed. [[pinned sys_arch.c L156–188]](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/lwip/port/freertos/sys_arch.c#L156-L188), [[L235–268]](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/lwip/port/freertos/sys_arch.c#L235-L268).
- The previously accepted A6b Linux fixture independently observed a real TCPIP task and `tcpip_try_callback()` admission / `ERR_MEM` under mailbox saturation. **It has not exercised `netconn_apimsg`, `sys_mbox_post`, `sys_arch_sem_wait`, `lwip_close`, or `tcp_close_ext` as this new close-specific test.** Source audit does not substitute for per-function SDK runtime observation.

### What an actual zero-network fixture can and cannot show

- The existing `tests/espidf_linux_probe/**` builds `IDF_TARGET=linux`, enables `CONFIG_LWIP_ENABLE=y`, uses actual `tcpip_init()`, static FreeRTOS synchronization, controlled TCPIP callback gates and a 20-second external executable watchdog. The current A6b case deliberately excludes socket and network operations. Its files and selective `linux-callback` CI route are current on this project baseline. A test-only `netconn_new(NETCONN_TCP)` / `netconn_delete()` extension is a **SOURCE-SUPPORTED FEASIBILITY CANDIDATE**, not an authorized implementation or verified binary. A no-netif `netconn_delete()` test could cover normal API-message teardown and deliberately held-TCPIP-core caller waiting, **not** connected-socket `lwip_close()` equivalence, TCP FIN `ERR_MEM`, FIN polling liveness, TLS close/free timing or complete HTTP cleanup. [[pinned tcp.c L331–405]](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/tcp.c#L331-L405), [[L1983–2009]](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/tcp.c#L1983-L2009).
- **Positive test candidate (separately authorized Codex only):** initialize real SDK TCPIP core with no netif; allocate `netconn_new(NETCONN_TCP)` from the application task; submit `netconn_delete()` on a separately owned *test worker* after a TCPIP callback is deliberately gated; prove no premature caller completion, release the gate, observe actual API-message completion and exact owner disposition, using finite watchdogs and strict final cleanup. Repeat under controlled mailbox saturation only if queue placement and ownership can be observed without SDK changes. This would prove only **a conditional close-path completion**, not a universal deadline.
- **Negative/STOP classification:** a queue-full worker that cannot be safely drained, non-completing API-message semaphore, or failed/delete-in-progress state must retain relevant owner storage until quiescence or terminate the isolated fixture; a test watchdog kill is **TEST_TERMINATION**, not cancellation, completion or resource reclamation. `tcpip_try_callback ERR_MEM` is not `tcp_close_ext ERR_MEM`. Reaching native FIN exhaustion on a connected PCB with zero networking, no socket and no SDK patch has **no demonstrated safe/reproducible path in the presently examined public surface**. Fabricating an ESTABLISHED PCB or intercepting FIN allocation would change evidence class and require a separate experiment design decision. No SDK or production source should be modified to force a PASS.
- **CI scoping:** current `tools/ci_scope.py` maps `tests/espidf_linux_probe/**` to `callback=true` only for an ordinary PR with unchanged protected workflows and no independently authorized full-matrix label; no CI was scheduled in this research. A new fixture implementation, worker/test-task creation or CI run requires **separate Codex Stage authorization**; a routing prediction is not actual CI evidence.
