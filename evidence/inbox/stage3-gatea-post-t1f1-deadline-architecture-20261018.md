## Pinned source identity and newly bounded routing conclusions

Project source: [ESP-IDF adapter](../../components/wfrac_transport_espidf/src/esp_http_transport.cpp) and [public ESP HTTP adapter header](../../components/wfrac_transport_espidf/include/wfrac_transport_espidf/esp_http_transport.hpp), project `eb68af889fea32af967b9c3f4447d2d085a6f62b`. SDK: ESP-IDF 6.0.2 `7101770dc6db2667b3c477cc31365dd1acd6db4e`; esp-lwIP `fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e`.

1. **SOURCE_CONFIRMED / adapter:** a per-call stack `ResponseCollector` points at caller-provided response storage, and the adapter passes its address through `esp_http_client_config_t.user_data`. The synchronous `perform()` calls blocking `esp_http_client_perform()` and always invokes `esp_http_client_cleanup()` before publishing a final return. Detached execution with that caller-owned stack/buffer would violate lifetime safety unless all asynchronous owners and outputs are redesigned; a task-externally forced client destruction is NOT authorized.
2. **SOURCE_CONFIRMED / async support restriction:** the pinned [ESP HTTP public header L218–226](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/include/esp_http_client.h#L218-L226) documents `is_async` as **HTTPS-only**; [perform L1471–1493](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/esp_http_client.c#L1471-L1493) returns `ESP_ERR_HTTP_EAGAIN` on particular in-progress phases. Changing `is_async` alone does not preserve the existing HTTP/HTTPS scheme contract and does not establish a global deadline.
3. **SOURCE_CONFIRMED / async still resolves synchronously:** [ESP-TLS async wrapper L608–616](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L608-L616) delegates to `esp_tls_low_level_conn()`, whose connect branch calls `esp_tls_hostname_to_fd()` and synchronous `getaddrinfo()` ([L221–255](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L221-L255), [L390–401](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L390-L401)). This source shows no independent operation-level cancellation/return bound for resolver completion. Reducing timeout or using a pre-resolved numeric IP can change this path but cannot silently replace the public hostname/TLS identity contract.
4. **SOURCE_CONFIRMED / cleanup remains synchronous and possibly not observable:** [HTTP cleanup L1101–1142](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/esp_http_client.c#L1101-L1142) discards close statuses; [ESP-TLS destroy L180–198](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L180-L198) calls socket `close()`. As shown in the [prior cleanup source dossier](stage3-gatea-cleanup-caller-return-source-20261017.md), pinned non-core-locking lwIP `netconn_apimsg` may block indefinitely on TCPIP mailbox admission or untimed semaphore completion, and close failure can be masked. `async perform` is not `async cleanup`.

## Requirement-to-solution separation

| Architecture candidate | L1 monotonic aggregate I/O | L2 deadline-expired caller notification | L3 quiescence and reclamation | Admission |
| --- | --- | --- | --- | --- |
| Current single blocking `perform+cleanup` + deadline checks | Partial cooperative accounting only; an SDK call may stall | Cannot return while its own thread is blocked | Unproven, possible masked close failure | **NO-GO** for universal synchronous hard bound |
| Flip `is_async=true` only | HTTPS-only + synchronous DNS / cleanup holes | No universal bound | Same close holes | **NO-GO** as a sole fix |
| Fixed-capacity owner task / supervisor, with copied input/output and caller detachment | Can impose supervisor *observation* budget for completed/unfinished task | **Conditional** if scheduling holds and timeout signal path remains live; no guaranteed task preemption | Cannot reclaim an arbitrarily stuck SDK operation; stranded worker/resource slot must be quarantined, never reused | Candidate only if user explicitly **relaxes** full quiescence/continued-availability expectation; production design NOT AUTHORIZED |
| New supported cancellable / nonblocking transport and teardown with bounded wait at every boundary | Potential target | Potential target | Potential target **only** after resolver, TCP/TLS teardown and scheduler/resource lifetime proof | Architecture R&D candidate; cannot claim feasibility now |
| Cooperative/best-effort policy | Not a hard bound | Late return possible | Cleanup can overrun | Requires explicit requirements change |

**Conditional worker design safety envelope, not code authorization:** bounded *total* task+stack+client+TLS+response storage; request-owned deep copies; no lifetime tied to caller stack; at most admitted concurrent worker slots; unknown/stuck slot is permanently retained or isolated until independently observed quiescence; exhausted capacity returns fail-closed, forbids retries/duplicate write side-effects, and reports degraded/unavailable service. The caller's timeout and the worker's cleanup-completed signal are distinct facts. Do not `vTaskDelete` a blocked owner, free TLS/HTTP/socket/buffer from another context, reuse DNS token, bypass hostname validation, disable TLS verification, abort TCP blindly or issue a new worker for every timeout. Scheduling stalls can delay even supervisor signal; hard wall-clock caller bounds still require separately proven scheduling/RTOS assumptions.

## Decision / next authorized boundary

**Engineering recommendation:** Do not implement the worker route or switch the SDK async flag until the user chooses whether the original **universal synchronous hard deadline + L3 full quiescence** must remain invariant, or a deliberately narrower caller-visible timeout + bounded quarantine / fail-closed degraded availability is acceptable. If strict invariant remains, current pinned SDK/adapter architecture is **NO-GO** as a proven design; first design and verify a genuinely bounded cancellable network/TLS/cleanup stack under a separate authorized engineering change. Further CLOSED-branch T1 repetition or synthetic F1 reruns cannot resolve that architectural blocker.

**Observed evidence classes:** `SDK_RUNTIME_CONFIRMED` = actual T1 CLOSED netconn 2/2 plus A6b 3/3 (prior accepted runs only); `SYNTHETIC_PASS` = F1 8/8 (prior); `SOURCE_CONFIRMED` = pinned async/DNS/cleanup path here; `INFERRED` = feasible bounded quarantine *only under explicit scheduler/ownership assumptions*; `UNPROVEN/NOT_RUN` = global L1/L2/L3 guarantees, native connected close/TLS runtime, permanent recovery.
