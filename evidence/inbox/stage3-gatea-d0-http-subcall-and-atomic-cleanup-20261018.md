## Exact accepted requirement

The 2026-10-12 [D0 contract in TASKS.md](../../TASKS.md) requires one monotonic budget across **controllable I/O**; it does **not** claim all SDK subcalls or cleanup are preemptible, nor universal hard `perform()` caller-return. L2 requires fail-closed response publication and one physical attempt; L3 requires safe lifecycle of application-owned resources and quarantine if unproven. [D0 interpretation reconciliation](stage3-gatea-d0-scope-reconciliation-20261018.md) supersedes later claims that a universal synchronous hard cap was already an accepted mandatory condition.

## Pinned ESP HTTP segmented-interface feasibility

- **Whole `perform()`**: project [`esp_http_transport.cpp` lines 72–123](../../components/wfrac_transport_espidf/src/esp_http_transport.cpp) sets `client_config.timeout_ms` once and invokes blocking `esp_http_client_perform()`. It has no per-effective-I/O monotonic deadline checks while the pinned SDK loops across its own operations.
- **`esp_http_client_open()` still contains internal work**: pinned [`esp_http_client.c` lines 1868–1888](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/esp_http_client.c#L1868-L1888) enters `esp_http_client_connect()` and `esp_http_client_request_send()`; the latter's [header send loop L1805–1829](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/esp_http_client.c#L1805-L1829) repeatedly calls `esp_transport_write(..., client->timeout_ms)`, not an externally refreshed aggregate remaining budget. The blocking connect still has DNS/TCPIP/TLS source-supported delays.
- **`esp_http_client_write()` is not necessarily one transport write**: pinned [L1891–1908](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/esp_http_client.c#L1891-L1908) loops until `len` bytes have been handled for synchronous mode, using the same `client->timeout_ms` on each underlying write.
- **`esp_http_client_fetch_headers()` is internally looping**: pinned [L1622–1650](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/esp_http_client.c#L1622-L1650) reads repeatedly until a complete header, with per-transport-read `timeout_ms`; a trickle of header bytes can extend a single public API call past an intended aggregate budget.
- **`esp_http_client_read()` also loops**: pinned [L1387–1468](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/esp_http_client.c#L1387-L1468) repeatedly reads while requested length remains; `esp_http_client_read_response()` [L2074–2084](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/esp_http_client.c#L2074-L2084) loops around that API again. `esp_http_client_set_timeout_ms()` [L1335–1343](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/esp_http_client.c#L1335-L1343) only mutates a per-client timeout value between calls; it cannot refresh timeouts *inside* an already executing call.

**SOURCE-CONFIRMED decision:** replacing `perform()` with `open/write/fetch_headers/read_response()` and setting remaining timeout **only at public-call boundaries** is **not sufficient** to establish D0 L1 aggregate checkpoints for trickle I/O or blocked internal loops. It may provide better observations for some phases but does not prove the contract. An independently controlled one-I/O-at-a-time path with monotonic checks remains a candidate only, not a source-proven solution to TCPIP/cleanup stalls.

## A more immediate L2/L3 issue in the current adapter

Project [`esp_http_transport.cpp` lines 107–124](../../components/wfrac_transport_espidf/src/esp_http_transport.cpp) reads HTTP success metadata, writes `response->http_status` and `response->body_size`, calls `esp_http_client_cleanup(client)` and **returns the previously computed result without using cleanup failure evidence**. This is an in-call early *metadata assignment*; it is not proof that another task actually read those fields before the synchronous call returned. The material issue is that **a failed lower-layer close can be masked and the returned result can still be `none`**. Pinned [`esp_http_client_cleanup()` L1101–1142](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp_http_client/esp_http_client.c#L1101-L1142) discards `esp_http_client_close()` result, frees context, and returns `ESP_OK` for a valid handle, so merely checking `esp_http_client_cleanup()` return **would not detect a failed close**. Prior [F1 evidence](stage3-gatea-cleanup-caller-return-source-20261017.md) showed the failure-masking pattern synthetically; this is the exact project success-path observation. Do not claim native socket leakage or violated runtime ownership without actual SDK evidence.

**D0 integration implication:** if teardown is not independently proven safe, success metadata must not be treated as an authoritative completed transport operation. A hypothetical D2 replacement must keep final response/result provisional until the chosen owner reaches a witnessed safe terminal state, or fail closed/quarantine on unknown close state. The existing public `ITransport` output is caller-owned and non-owning; changing it or deploying a separate worker is not authorized.

## ESP-TLS preconnected socket handoff is not established by the setter alone

**Pinned API/source finding — SOURCE_CONFIRMED, client handoff runtime UNPROVEN:** ESP-TLS exposes `esp_tls_set_conn_sockfd()` and `esp_tls_set_conn_state()`. The former only assigns `tls->sockfd = sockfd`, and the latter only stores a selected state in `tls->conn_state` ([`esp_tls.c` L769–796](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L769-L796)). A successful setter return **does not** prove SSL client configuration, TLS handshake, hostname/SNI binding, certificate verification or lifecycle transfer.

- On normal `esp_tls_conn_new_async()` entry, the SDK continues via `esp_tls_low_level_conn()`; its `ESP_TLS_INIT` branch **resets** `tls->sockfd=-1` and calls its own `tcp_connect(hostname,...)` ([`esp_tls.c` L488–516](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L488-L516), [L610–615](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L610-L615)). Thus **setting a socket fd alone before ordinary client connection does not bypass** internal resolver/socket setup.
- The state setter means alternate state-machine paths could be hypothesized, but this is **not a validated or documented, full preconnected-client TLS handoff contract**. In the `ESP_TLS_CONNECTING` path, `create_ssl_handle(hostname,...)` is invoked after other state/FD checks, binding `mbedtls_ssl_set_hostname` to the caller-specified or configured hostname ([`esp_tls.c` L518–558](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L518-L558), [`esp_tls_mbedtls.c` L908–937](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls_mbedtls.c#L908-L937)). Forcing this entry point externally would require independent evidence for prepared internal state, ownership, configurations, error paths and cleanup. Do not claim that the setter creates a supported/preverified session, nor declare every possible alternate route impossible without testing.
- Pinned `esp_tls_conn_destroy()` still calls lower-level deletion and then `close(tls->sockfd)` before freeing the context, with no independent hard-bound close promise ([`esp_tls.c` L180–198](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L180-L198)). Any external fd ownership handoff would require an explicit exactly-once close owner and close-error/quiescence evidence. Passing a borrowed descriptor into a context that may close it is not automatically safe.

**Architecture triage:** a bespoke one-I/O-at-a-time mbedTLS BIO, with verified hostname/SNI and certificate chain, remains a conditional D0 design candidate. ESP-TLS `set_conn_sockfd` + `set_conn_state` is **not admitted as a production shortcut**. Any exact-state test of preconnected client handoff would be new, separately authorized Codex test-only work; it cannot be upgraded from source observations alone.
