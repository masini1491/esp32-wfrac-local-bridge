# Stage 3 Gate A — L3: close completion is not TCP PCB reclamation

**Date:** 2026-10-18 (Asia/Taipei). **Project baseline:** `main@2db3e5cb607c92f00d301b0d0dbff70b4c554450`; **source pins:** ESP-IDF 6.0.2 `7101770dc6db2667b3c477cc31365dd1acd6db4e`, esp-lwIP `fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e`. **Evidence:** exact pinned source and official lwIP semantics, **SOURCE_CONFIRMED**; no new SDK runtime, memory exhaustion test, CI, network traffic, production source, SDK patch, firmware or hardware activity. Complements [previous bounded close dossier](stage3-gatea-cleanup-caller-return-source-20261017.md) and [BSD nonblocking study](stage3-gatea-bsd-nonblocking-api-message-20261018.md). This is a coordination evidence note, not a replacement for the canonical D0 acceptance contract.

## Three different terminal observations

1. **Application API completion / descriptor disposition:** pinned [`lwip_close()` in sockets.c L817–855](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/sockets.c#L817-L855) calls `netconn_prepare_delete()`; if it fails, it returns -1 without calling `free_socket()`. If it succeeds, socket-level storage is released and 0 returned. This is an **API result**, not proof that a connected TCP PCB has been freed or that all unrelated application-side callbacks have quiesced.
2. **Application handle / callback quiescence:** pinned [`lwip_netconn_do_close_internal()` L1004–1023 and L1109–1136](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/api_msg.c#L1004-L1136) clears TCP application callbacks on the successful whole-close path, sets `conn->pcb.tcp=NULL`, and wakes the application's completion semaphore. This happens **after** the core callback executes and is conditional on its success path; not a universal guarantee that no blocked worker, DNS token, TLS callback or external owner remains. Independent observation of those owners remains required for Gate A L3.
3. **Protocol PCB lifetime / quiescence:** the pinned official source documentation in [`api_lib.c` L185–189, L226–233](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/api_lib.c#L185-L233) expressly says TCP PCBs may remain in a wait state after `netconn_prepare_delete()` or `netconn_delete()` returns. For an established connection, [`tcp_close_shutdown_fin()` L408–459](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/tcp.c#L408-L459) can move to `FIN_WAIT_1` / `LAST_ACK`, with future timer or peer acknowledgment progression. Pinned [`tcp_slowtmr()` L1451–1480](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/tcp.c#L1451-L1480) frees `TIME_WAIT` PCBs only after its `2 * TCP_MSL` tick condition, assuming timer execution. Ordinary protocol waiting is **not by itself a leak**; neither does `close()==0` prove instantaneous zero-PCB reclamation.

## Additional conditional `ERR_MEM` case, source-confirmed only

- In an established TCP close, pinned [`tcp_close_shutdown_fin()` L442–457](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/tcp.c#L442-L457) sets `TF_CLOSEPEND` when FIN allocation fails with `ERR_MEM` and deliberately returns `ERR_OK` to the caller; [`tcp_fasttmr()` L1507–1518](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/tcp.c#L1507-L1518) may later retry pending FIN. Pinned [`api_msg.c` L1024–1065](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/api_msg.c#L1024-L1065) calls `tcp_close_ext()` and regards its `ERR_OK` as close-finished. Therefore even `close` success **need not mean FIN has been queued/sent or a connected PCB reclaimed**. Whether this exact path occurs under pinned target configuration and memory pressure remains **NOT_RUN / UNPROVEN**; do not turn it into a measured problem report. Distinguish it from the separate `lwip_netconn_do_close_internal()` retry-on-`ERR_MEM` path, which applies only if `tcp_close_ext()` actually propagates `ERR_MEM`.
- In `LWIP_NETCONN_FULLDUPLEX` mode, pinned [`api_msg.c` L1166–1250](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/api_msg.c#L1166-L1250) can signal `ERR_CLSD` to an in-progress blocking connect/write while separately tracking close processing, including Espressif-specific `ERR_INPROGRESS` cases. This conditional interruption still requires the TCPIP thread to execute and the terminal resource disposition to be independently established. Not a hard deadline or universal cancellation proof.

## Implications for original L1/L2/L3 acceptance

| Witness required | Sufficient only for | Not sufficient for |
| --- | --- | --- |
| `close()==0` or `netconn_delete()==ERR_OK` | An observed API-completion branch | Full protocol PCB reclamation, TLS owner cleanup, all callbacks quiesced, unconditional caller deadline |
| All application-owned callbacks/handles independently completed and invalidated | Scoped application-level lifecycle quiescence | Guarantee of zero normal TCP protocol `FIN_WAIT/TIME_WAIT` residue or scheduler progress under arbitrary stall |
| TCP PCB timer/FIN/ACK observations | Protocol progression in measured cases | Caller hard bound under permanent TCPIP scheduler stall |
| Watchdog termination of test process or device reset | Termination / system reset only | Per-request safe reclamation or normal close completion |

**D0 contract must remain unchanged** until a separate architecture decision. The observable L3 acceptance definition should explicitly say whether it requires (a) safe reclamation/quiescence of **application-owned** callback, client, TLS and socket references while permitting documented finite TCP protocol wait states, or (b) literal zero residual TCP PCBs before caller return. Source evidence shows (b) is incompatible with normal connected TCP close without an independently proven waiting period; it is **not authorized** to silently relax (b) to (a). Either formulation still has unresolved caller return under blocked API-message delivery and unreclaimable owners if the TCPIP thread does not progress.

**Next bounded evidence decision:** a future separately authorized no-egress test-only T2 could instrument actual pinned *unconnected* socket-close status and application owners; it cannot establish connected FIN retry/TIME_WAIT or absence of all callbacks. To exercise native connected close/FIN under strict zero-network restrictions would need a separately reviewed fixture feasibility and transport-safety admission; no fabricated connected PCB or unapproved network/SDK patch. Repeating existing T1 CLOSED-only / F1 synthetic does not prove these additional conditions.
