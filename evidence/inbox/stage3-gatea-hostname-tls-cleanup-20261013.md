## Specific source conclusions

1. **Existing ESP-TLS async is NOT nonblocking hostname resolution.** `esp_tls_conn_new_async()` enters `esp_tls_low_level_conn()` → `tcp_connect()` → `esp_tls_hostname_to_fd()` → synchronous `getaddrinfo()`. `esp_tls_set_conn_sockfd()` only assigns `tls->sockfd`; the exposed setter by itself does NOT prove an officially supported, already-connected client TLS handshake path that bypasses `tcp_connect()`. Source: [esp_tls.c#L221-L248](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L221-L248), [#L386-L403](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L386-L403), [#L489-L531](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L489-L531), [#L610-L618](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L610-L618), [#L769-L777](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L769-L777).
2. **An actual async DNS option exists, but its callback lifetime is unproven for this synchronous adapter.** The pinned lwIP raw `dns_gethostbyname_addrtype()` expressly returns `ERR_INPROGRESS` with later `dns_found_callback`. The public pinned `lwip/dns.h` examined does not declare a per-request cancellation function. The DNS request table stores the callback and caller argument until callback processing. An adapter may NOT pass a stack/caller-owned pointer that could expire at timeout; any bounded owner/retained request/callback quiescence strategy requires separate design, test and context/thread-affinity verification. Source: [dns.c#L1669-L1740](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1669-L1740), [dns.c#L1525-L1560](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1525-L1560), [dns.c#L1049-L1081](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1049-L1081), [dns.h#L95-L113](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/include/lwip/dns.h#L95-L113).
3. **Physical IP and certificate/SNI name are distinct.** `set_client_config()` chooses caller-supplied `cfg->common_name` if present, otherwise connection `hostname`; it passes the selected string to `mbedtls_ssl_set_hostname()`. `skip_common_name=true` disables BOTH hostname matching and SNI and is unacceptable as a silent workaround. The project TLS owner already records some observed self-signed WF-RAC HTTPS certificates with IP/CN mismatch. Therefore a literal-IP connection is not automatically authenticated: require explicitly trusted peer identity, usable PEM trust and correct name/certificate evidence; none is hardware-confirmed for the proposed adapter. Source: [esp_tls_mbedtls.c#L913-L940](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls_mbedtls.c#L913-L940), [esp_tls.h#L198-L207](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.h#L198-L207), [local TLS policy](https://github.com/masini1491/esp32-wfrac-local-bridge/blob/c2efa3ffa83d7fac901f19dc860aebb284a5a5fa/docs/references/topics/tls-transport.md).
4. **Nonblocking socket does not prove bounded cleanup.** `esp_tls_conn_destroy()` frees TLS and calls `close(tls->sockfd)`. In pinned lwIP, `lwip_close()` calls `netconn_prepare_delete()`, which can enter `netconn_apimsg`. The TCP close code explicitly handles `ERR_MEM` by waiting and states this may occur **even for nonblocking netconns**. L1 cooperative I/O budget is separate from hard wall-clock caller-return, cancellation and L3 quiescence; no source proof of a universal cleanup bound. Source: [esp_tls.c#L180-L195](https://github.com/espressif/esp-idf/blob/7101770dc6db2667b3c477cc31365dd1acd6db4e/components/esp-tls/esp_tls.c#L180-L195), [sockets.c#L817-L842](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/sockets.c#L817-L842), [api_lib.c#L195-L225](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/api_lib.c#L195-L225), [api_msg.c#L1068-L1110](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/api_msg.c#L1068-L1110).

## 2026-10-13 follow-up — raw DNS callback ownership / shutdown gate

**Research disposition:** source-backed architecture candidate **REFERENCE-ONLY**, not production adoption. No new SDK/host/network/hardware tests were run in this follow-up; retain D1 test evidence with original provenance. No runtime or implementation authority expands.

### New source-confirmed behavior and consequences

- Pinned lwIP `dns_gethostbyname_addrtype()` is a raw callback API: `ERR_OK` returns a parsed/cached address immediately; `ERR_INPROGRESS` leaves `dns_found_callback` and `callback_arg` inside DNS request bookkeeping. `dns_call_found()` dispatches callbacks on success/failure; timeout/retries are driven by `dns_tmr()` and `dns_check_entry()`, not by `TransportRequest.timeout_ms`. The default generic `DNS_MAX_RETRIES` value is 4 in upstream `opt.h`, but actual timeout also depends on retries, fallback DNS servers, configuration, scheduler/timer progress. Do **not** equate DNS retry exhaustion with a strict caller deadline. Evidence: [dns.c#L1525-L1658](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1525-L1658), [dns.c#L1049-L1081](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1049-L1081), [dns.c#L1145-L1255](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1145-L1255), [dns.c#L1669-L1810](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L1669-L1810).
- `dns_clear_cache()` iterates every live DNS table entry, can issue `dns_call_found(..., NULL)` and then clears the global table. It is **not** a safe per-request timeout/cancellation tool; it can disrupt unrelated lookups. No per-request cancel function was found in the examined public `lwip/dns.h`; absence from this header is **not proof** that no project/port-specific cancellation mechanism can ever exist. Evidence: [dns.c#L405-L420](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/core/dns.c#L405-L420), [dns.h#L99-L116](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/include/lwip/dns.h#L99-L116).
- Raw lwIP APIs and the socket/netconn APIs have **different concurrency/ownership contracts**. Pinned lwIP describes TCPIP-core locking or core-thread callbacks for raw operations; `tcpip_callback()`/`tcpip_try_callback()` offer dispatch surfaces but their enqueue and completion do not themselves establish a bounded wall-clock outcome. Do not call raw DNS from an arbitrary application task without proving correct core context/locking and callback ordering on the exact ESP-IDF build. Evidence: [opt.h#L174-L229](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/include/lwip/opt.h#L174-L229), [tcpip.h#L71-L89](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/include/lwip/tcpip.h#L71-L89).
- Even numeric `getaddrinfo()` can be a synchronous API. Pinned `lwip_getaddrinfo()` has a no-DNS `AI_NUMERICHOST` path (parse-only); this does not make ESP-TLS's unqualified `getaddrinfo()` call a universal hard-deadline guarantee or provide hostname support. Evidence: [netdb.c#L418-L496](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/netdb.c#L418-L496).
- Pinned `lwip_close()` routes through `netconn_prepare_delete()` and TCP close can wait after `ERR_MEM`, including nonblocking sockets. `SO_LINGER=0`/abort-style suggestions do **not** prove strict full-call bound and may change on-wire semantics; `LWIP_SO_LINGER` is configuration-dependent. Avoid direct `tcp_abort()` of a socket-owned PCB without supported ownership evidence. Evidence: [sockets.c#L817-L842](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/sockets.c#L817-L842), [api_lib.c#L195-L225](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/api_lib.c#L195-L225), [api_msg.c#L1027-L1110](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/api/api_msg.c#L1027-L1110), [opt.h#L2108-L2115](https://github.com/espressif/esp-lwip/blob/fd432e4ee2cfb7f7f1c7eb7227e0173412e7b84e/src/include/lwip/opt.h#L2108-L2115).

### Gate A3 design candidate — bounded retained DNS request owner (NOT ACCEPTED, no code mutation)

1. **Separate lifetimes:** User `perform()` stack, request-owned output buffer and response struct must not be referenced by DNS callback; a stable separately owned and bounded resolver slot (hostname/key, generation/token, result address, terminal flag and synchronization) must outlive any registered callback. The callback never writes into caller buffers, protocol/Device Model, SchemePolicy or TLS state.
2. **Owner lifecycle:** conceptual `FREE → REGISTERING → DNS_PENDING → (RESOLVED | TIMED_OUT_DETACHED | ERROR) → CALLBACK_QUIESCENT → RECLAIMABLE`. Only the **caller** can decide request deadline; only proven DNS callback/registration quiescence can permit slot reuse. A late reply to a timed-out generation is discarded without reopening the transport or counting as success. Specify ordering and thread context for atomic states before considering implementation.
3. **Bounded resources vs liveness:** fixed slot capacity and explicit exhaustion error/STOP. If a DNS callback fails ever to arrive, the slot cannot be unsafely freed; the system can become temporarily or indefinitely unable to start further hostname requests. This preserves a bounded memory footprint and avoids UAF but is **not** proof of resource quiescence, eventual reclamation or service availability. Reusing slots via generation check alone cannot prevent a stale raw `void *` pointer from referencing memory that has been freed and reallocated.
4. **Single-attempt/timing:** hostname resolution may be shared/pre-existing cached input only with explicit ownership and no hidden network attempt/retry; one physical HTTP attempt remains. Time spent posting to TCPIP core, DNS completion, TCP connect, TLS handshake, HTTP and cleanup must each be classified by actual controllable-wait and unpreemptible boundaries. Pinned `esp_tls_conn_new_async`'s getaddrinfo path cannot be used as an all-stage bounded shortcut.
5. **TLS identity:** physical connect address, logical `TransportEndpoint.host`, optional explicit `EspTlsVerificationConfig.common_name`, HTTP Host and trust roots are separate concepts. Preserve user-approved meaning and certificate-chain / SNI / hostname checks, never `skip_common_name`. A newer design must prove which identity string is actually authenticated; observed WF-RAC self-signed/IP-CN mismatch remains hardware-unverified for the replacement.

**Required bounded next proof (separately admitted Codex offline-test scope, NOT run):** simulated `ERR_OK/ERR_INPROGRESS/ERR_MEM/ERR_ARG`, pending/late success and failure, DNS cache clear, duplicate name queries, timer/scheduler stall, multiple DNS server failover, pre/post-enqueue timeout, core dispatch failure, TLS identity mismatch, generation reuse, fixed slot exhaustion, callback after caller return, teardown before/after callback, close `ERR_MEM`/cleanup overrun. Verify no callback can access caller stack or released buffer; never claim these fakes validate real TCPIP-thread callback ordering, memory life, SDK build or hard cleanup upper bounds. If some lifecycle guarantee is unprovable, retain explicit STOP and request owner/architecture decision rather than modifying production.

**Current decision:** Preserve public hostname + TLS security contracts. Prefer a retained bounded owner only as a *candidate* for DNS-timeout fail-closed behavior; no basis yet to promise complete quiescence or total synchronous hard caller-return. To actually guarantee returning to the caller at a strict deadline while a possibly blocking cleanup remains pending, a separately owned worker/supervisor or SDK-level cancellation approach is an **architectural change requiring separate explicit user authorization**. There is no supported proof that the worker's cleanup itself has a hard upper bound. Stage 3 Gate A implementation feasibility **PENDING / NOT PASS**; Gate B ON HOLD; Stage 4 Cold; Library readiness PRESERVED.
