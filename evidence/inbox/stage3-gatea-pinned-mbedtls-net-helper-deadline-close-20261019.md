## Newly confirmed source differences

1. **Two distinct zero-timeout semantics — important for D0 L1.** Pinned [`net_sockets.h` L164–186](https://github.com/Mbed-TLS/mbedtls/blob/6cc42afad309e861f4c07e6f106e2ab14a9cb8e5/include/mbedtls/net_sockets.h#L164-L186) and [`net_sockets.c` L441–502](https://github.com/Mbed-TLS/mbedtls/blob/6cc42afad309e861f4c07e6f106e2ab14a9cb8e5/library/net_sockets.c#L441-L502) specify `mbedtls_net_poll(timeout=0)` as an **immediate poll**, with `UINT32_MAX` (`-1u`) representing an indefinite wait. By contrast, [`net_sockets.h` L249–270](https://github.com/Mbed-TLS/mbedtls/blob/6cc42afad309e861f4c07e6f106e2ab14a9cb8e5/include/mbedtls/net_sockets.h#L249-L270) and [`net_sockets.c` L569–611](https://github.com/Mbed-TLS/mbedtls/blob/6cc42afad309e861f4c07e6f106e2ab14a9cb8e5/library/net_sockets.c#L569-L611) define `mbedtls_net_recv_timeout(timeout=0)` as **potentially infinite blocking**, even on a nonblocking socket; it passes no timeval to `select()` for zero. Copying the same `remaining_ms` directly to both APIs can accidentally turn expired D0 budget into an unbounded receive. The source finding is independent of whether the project has built/enabled `MBEDTLS_NET_C`.
2. **`mbedtls_net_poll()` internally retries `EINTR` without an aggregate clock check.** Exact pinned [`net_sockets.c` L482–488](https://github.com/Mbed-TLS/mbedtls/blob/6cc42afad309e861f4c07e6f106e2ab14a9cb8e5/library/net_sockets.c#L482-L488) calls `select` in a `do … while(IS_EINTR(ret))` loop. It does not ask the caller to recompute an attempt-wide monotonic remaining budget between interruptions; its own `timeval` is not an independently verified absolute deadline. This is **not observed starvation**, but `net_poll` alone is insufficient as evidence that D0 checks the shared budget after every controllable wait/EINTR.
3. **`mbedtls_net_close()` and `mbedtls_net_free()` both hide socket close failure.** [`net_sockets.c` L658–682](https://github.com/Mbed-TLS/mbedtls/blob/6cc42afad309e861f4c07e6f106e2ab14a9cb8e5/library/net_sockets.c#L658-L682) shows `mbedtls_net_close` calling `close(fd)`, unconditionally storing `fd=-1`, returning `void`; `mbedtls_net_free` calls `shutdown(fd,2)` then `close(fd)`, ignores both results, unconditionally stores `fd=-1`, and returns `void`. A `-1` descriptor after these helpers is a **local handle-state observation**, not proof that underlying socket closure succeeded or all application-owned callbacks are quiesced. Pinned esp-lwIP may return a close error while retaining resource ownership, as previously recorded in [L3 close evidence](stage3-gatea-l3-close-ack-versus-pcb-reclaim-20261018.md). No new native failure or leak was demonstrated.
4. **Nonblocking BIO can be defined without timed receive helper.** [`mbedtls_ssl_set_bio` L2129–2163](https://github.com/Mbed-TLS/mbedtls/blob/6cc42afad309e861f4c07e6f106e2ab14a9cb8e5/include/mbedtls/ssl.h#L2129-L2163) explicitly supports `f_recv` without `f_recv_timeout`. Exact pinned [`mbedtls_net_send` L617–653](https://github.com/Mbed-TLS/mbedtls/blob/6cc42afad309e861f4c07e6f106e2ab14a9cb8e5/library/net_sockets.c#L617-L653) and [`mbedtls_net_recv` L528–564](https://github.com/Mbed-TLS/mbedtls/blob/6cc42afad309e861f4c07e6f106e2ab14a9cb8e5/library/net_sockets.c#L528-L564) map would-block/interrupt into WANT_WRITE/WANT_READ on appropriate nonblocking descriptors. However actual esp-lwIP socket creation/nonblocking setup, TCPIP message wait and teardown remain separate operations without new timing guarantees; this is **API precedent**, not a working D0 transport.

## Scope-limited design consequences

- **L1 proposed control:** Before any network operation and after every returning WANT/EINTR/wakeup, check the same monotonic budget; on expiry stop new I/O and avoid all ambiguous zero/maximum timeout sentinels. If using a polling helper with internal EINTR retry, classify that nested wait as an unproven checkpoint unless wrapped in independently bounded behavior; choosing a private readiness loop with explicit recomputation is a candidate but remains subject to pinned lwIP syscall limitations.
- **L2 unchanged:** Keep TLS hostname/SNI + CA verification and exactly one physical request, atomic success publication after accepted response and safe terminal owner observation. No scheme fallback or resend following a possibly-delivered write.
- **L3 proposed control:** Distinguish `close_notify` (TLS peer alert), `mbedtls_ssl_free` (SSL context release) and socket `close` return + DNS callback fence (lower-layer/application owner). Do not treat `mbedtls_net_free/close` as an observable close witness, and do not automatically retry a close with uncertain descriptor ownership. Quarantine or STOP conflicting attempts when safe application-resource quiescence remains unknown.
- **Evidence boundary:** A bounded future **test-only** host negative model may inject timeout=0 / UINT32_MAX, repeated EINTR, WANT retries and fake close failure; a separate pinned **compile-only** fixture could check mbedTLS/BIO API signatures and C3/C6 Kconfig/link. Neither may be called native runtime proof. Actual failure-observable close and connection lifecycle require separate safe fixture and task authorization. No network/hardware, SDK, workflow, product source changes are admitted.

**Disposition:** Supported direct mbedTLS/BIO remains a conditional architecture direction, now with explicit helper restrictions. This study is not Gate A PASS and does not create an implementation Stage. Existing PR #17 test-only D2 26/26 SYNTHETIC_PASS and D1 36/36 PASS remain valid within their original scopes.
